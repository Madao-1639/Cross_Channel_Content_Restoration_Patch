# 问题记录与经验教训

本文档记录 CROSS†CHANNEL 内容还原补丁项目中遇到的问题和经验教训。

## 从 A Sky Full of Stars 项目迁移的经验

### 1. Unicode 编码错误

**问题**：Windows 控制台默认 GBK/cp936，print 非 ASCII（✓/✗/中文）会 `UnicodeEncodeError` 中断脚本。

**解决方案**：
- 脚本开头加 `sys.stdout.reconfigure(encoding='utf-8')`（包在 try/except 里）
- 或统一用 `[OK]`/`[!]` 等 ASCII 标记

### 2. PNA 引用错配

**问题**：改写引用时使用简单字符串替换导致双前缀问题。

**错误示例**：
```python
# ❌ 错误做法
dec.replace('TCCT1000', 'ORG_TCCT1000')
```

这会命中已是 `ORG_TCCT1000` 名字的**尾巴**，把已改好的名再改一次 → 双前缀 `ORG_ORG_TCCT1000`。

**正确做法**：
```python
# ✅ 正确：用带 NUL 前缀的精确模式
dec.replace(b'\x00' + old_name, b'\x00' + new_name)
```

显示指令格式为 `<slot>\x00NAME.PNA\x00`，使用 NUL 前缀可以精确匹配。

**附加原则**：
- 每次运行时先检查"已满足则跳过"，保证脚本重复运行安全（幂等性）
- 改写后必须回读验证

### 3. 日文文件名识别

**问题**：脚本中带日文的资源名是 Shift-JIS 编码，不是 UTF-8。

**影响**：
- 搜索/改写资源引用必须用 `name.encode('shift_jis')` 构造字节模式
- 标准正则 `[A-Za-z0-9_]+` 匹配不到含日文的名字，审计时极易漏掉

**解决方案**：
```python
# 正确处理日文资源名
resource_name = 'TCCT1000'  # 如包含日文
byte_pattern = resource_name.encode('shift_jis')
```

### 4. 资源缺失卡死

**问题**：原版脚本引用了 Steam 已删除的背景/特效 PNG，引擎在硬载入时找不到文件，直接无响应（卡死），不弹任何错误码。

**症状**：
- `0x33` 硬载入缺失资源 → 卡死（无响应）
- `0x66` 遮罩缺失 → 容忍（静默跳过，仅画面瑕疵）

**解决方案**：从原版补入 Steam 已删的背景/特效 PNG。

**定位方法**（可复用）：
1. **台词 → 脚本偏移**：在 lng 中定位台词，再到解码后脚本里找到对应位置
2. **偏移 → 指令**：`ws2.decode()` 后按偏移解析紧随其后的 `0x33/0x34/0x66` 资源引用
3. **三方资源审计**：枚举脚本全部资源引用，逐一对 Steam 与原版目录求交集，筛出"仅原版存在"的资源

### 5. Arc 文件 Null Padding 导致哈希不一致

**问题**：某些 Arc 文件在表结束位置有 null padding（`\x00\x00`），位于表和数据段之间。`arcbuild.write_arc()` 不保留这个 padding，导致每次读写都产出不同的 SHA256，安装器哈希校验失败。

**症状**：
- 源文件 SHA256 ≠ 安装后文件 SHA256（相差 padding 字节数）
- 重复写入产生不同哈希（非幂等）
- 安装器验证失败

**解决方案**：
1. **规范化源文件**：运行一次 `arcbuild.normalize_arc_padding()` 去除 padding
2. **防护机制**：`arcbuild.verify()` 现已加入检查，如果发现 padding 会抛出错误
3. **确保幂等性**：规范化后，任何读写都产生相同哈希

**代码示例**：
```python
import arcbuild
from pathlib import Path

arc = Path('releases/Rio.arc')

# 规范化（去除 padding）
size = arcbuild.normalize_arc_padding(arc)
print('Normalized to {} bytes'.format(size))

# 验证（现已检查 padding）
cnt, fsize, end = arcbuild.verify(arc)
```

### 11. 原版游戏引擎与 Steam 版不兼容

**授权提醒**：`CROSS_CHANNEL_Original/readme.txt` 声明"未经允许不得以任何理由对本补丁进行破解分析，即使是出于学习的目的"。本节记录的是只读结构分析（识别脚本/资源对应关系以支持内容还原），未逆向或再分发汉化组的破解手段本身。

**问题**：起初假设原版游戏（民间汉化版）可作为 Steam 版缺失资源的补充来源（`CLAUDE.md` 的"资源补全"方案）。

**发现**：分析原版游戏本体（`CROSSCHANNEL.exe`）后确认，其引擎与 Steam 版（`AdvHD.exe`，MoeNovel Amaneko 系）是完全不同的实现：

| 特性 | 原版（CROSS_CHANNEL_Original） | Steam 版 |
|------|-------------------------------|---------|
| 主程序 | `CROSSCHANNEL.exe` | `AdvHD.exe` |
| 脚本格式 | `WSC`（无 rot6 混淆，纯二进制） | `WS2`（rot6 混淆） |
| 立绘格式 | 未见 PNA，走 `ANM`/`MSK` 等分类 tag | PNA 图层 |
| 特征字符串 | 无 `AdvHD`/`WS2`/`PNA`/`lua` | 有 `PNA`/`lua` |
| 版权声明 | WillPlus/CROSSCHANNEL Co., Ltd. | MoeNovel（Amaneko 系 AdvHD 引擎） |

原版 Arc 归档格式（仅供参考，非本项目使用格式）：
```
[u32 tag_count]
[tag: 4s magic][u32 table_size][u32 data_start] × tag_count
[Entry: 13s name(null-padded)][u32 size][u32 rel_offset] × N  # 固定 21 字节/条
[Data region]
```
名字字段固定 13 字节 null 填充，与 Steam 版 UTF-16LE 变长名字完全不同，条目记录也不通用。

**影响**：无法把原版的 Rio.arc/Chip.arc/Voice.arc 等文件解包后直接塞进 Steam 版，此前"从原版补入资源"的方案不可行。

**对本项目的实际价值**（只读参考，不作资源来源）：
1. **翻译校对**：原版追加剧本 PDF 和汉化组 STAFF 名单可用于核对 Res 303 机翻部分的准确性（可选，非强制）
2. **场景编号验证**：原版脚本清单可用于核对 Res 303 12 个 H 场景插入点是否覆盖了原版对应的全部场景（调用链的独立验证信源）
3. **WSC 解密**：原版 WSC 解密算法（`ror 2`）已破解（详见第 2 节），可从原版读取真实对话内容供 lng 校对参考

## 最佳实践

### 脚本改写原则

1. **精确匹配**：使用显示指令上下文（带 NUL 前缀）进行替换
2. **幂等性**：脚本必须可重复运行，每次检查"已满足则跳过"
3. **回读校验**：改写后必须回读验证，确认修改成功
4. **编码正确**：日文资源名使用 Shift-JIS 编码

### 验证清单

改写脚本后必须执行：

- [ ] 调用链完整性检查
- [ ] 资源配对验证（`*_h` ↔ `ORG_*`，`*_en` ↔ Steam 资源）
- [ ] 资源存在性验证（所有引用的资源都存在）
- [ ] 冗余检测（无重复脚本、无未使用的 ORG_* 资源）
- [ ] Arc 文件规范化检查（运行 `arcbuild.verify()` 检测 null padding）
- [ ] SHA256 校验稳定性（修改后重新读写一遍，验证 SHA256 保持一致）

### 调试技巧

1. **遇到卡死无响应**：
   - 定位最后一句台词的位置
   - 检查紧随其后的 `0x33` 资源引用
   - 验证该资源是否存在

2. **遇到渲染失败或崩溃**：
   - 检查是否存在同名 PNA 冲突
   - 检查请求的 layer_id 是否超出 layer_count

3. **场景结束后流程异常**：
   - 检查跳转目标是否正确
   - 检查后缀是否一致

4. **文本显示异常**：
   - 检查 lng 文件是否存在
   - 检查字体文件是否支持汉字
   - 检查文本编码是否正确

5. **安装器哈希校验失败**：
   - 源 Arc 文件可能存在 null padding
   - 运行 `arcbuild.verify(path)` 检测是否有 padding
   - 规范化命令：`arcbuild.normalize_arc_padding(path)`

### 9. Chip2.arc 事件 CG 命名白名单机制

**问题**：测试场景 CNR0005_EN 时发现背景一直显示为黑屏，即使引用的 CG 文件（CN_EVCC0002.PNG → CN_EVCC0002B.PNG）存在于 Chip2.arc 中。

**根本原因**：Steam 版引擎对 Chip2.arc 中的事件 CG 文件名实施**前缀白名单机制**，只认可 `EVCC` 开头的文件，而 `CN_EVCC` 前缀被引擎完全忽略（不报错，但不加载）。

**证据**：
- Steam 原版 Chip2.arc 包含 199 个 PNG 文件，全部使用 `EVCC` 前缀（如 EVCC0021A.png、EVCC0114B.png 等）
- 没有任何 `CN_` 前缀的文件
- 补丁中添加的 36 个 `CN_EVCC*.PNG` 文件虽然存在，但引擎不加载

**解决方案**：采用 `EVCC9XXX` 命名格式
- 前缀：`EVCC`（白名单认可的前缀）
- 编号：从 9000 开始递增（避免与原版 EVCC0001-EVCC0118 冲突）
- 后缀：保留原始变体后缀（A/B/C）

**重命名映射**（36 个文件）：
```
CN_EVCC0002.PNG  → EVCC9000.PNG
CN_EVCC0002B.PNG → EVCC9001B.PNG
CN_EVCC0012.PNG  → EVCC9002.PNG
...
CN_EVCC0048B.PNG → EVCC9035B.PNG
```

**影响范围**：
- `payload/Chip2_patch.arc`：36 个 CG 文件重命名
- `asset/Rio.arc`：11 个脚本中的引用更新（CNR0001-CNR00011、CNR0105）

**实施工具**：`script/rename_cn_evcc_to_evcc9xxx.py`

**经验教训**：
1. **引擎可能对特定资源类型实施命名白名单**，不仅限于槽位前缀
2. **白名单违规不报错**，只是静默忽略，导致排查困难
3. **命名规范应遵循 Steam 原版模式**，避免自创前缀
4. **测试时需验证资源实际加载**，不能仅检查文件存在性

### 12. CN_EVCC9XXX 重命名遗漏 3 个后补脚本的引用

**问题**：`final_verification.py` 的"资源配对"检查发现 `CNR00009_en.ws2`、
`CNR00010_en.ws2`、`CNR00011_en.ws2` 仍引用旧的 `CN_EVCC*` 名字（10 处唯一引用，
共 48 次出现），而 `Chip2.arc` 中对应资源已在第 9 节的重命名中改为 `EVCC9XXX`。

**根本原因**：这 3 个脚本对应的调用链（CCD1001B/CCD4003A/CCD5001A）是在
`rename_cn_evcc_to_evcc9xxx.py` 首次运行**之后**才补充进 `asset/Rio.arc` 的，
因此从未被那次重命名扫描到。

**修复**：新增 `script/fix_cn_evcc_leftover_refs.py`。由于原始重命名映射表所在的
备份文件已被后续操作清理，脚本改为从 res303 `Graphic.arc` 中排序后的
`CN_EVCC*` 名字列表、与 `asset/Chip2.arc` 中按写入顺序排列的 `EVCC9XXX*` 名字列表
按位置一一对应，确定性地重建出等价的映射表（两份列表长度均为 36，顺序对应关系
由 `build_chip2()` 的实现方式保证）。重建后扫描 `asset/Rio.arc` 全部 `.ws2`
成员，仅替换匹配到的 `CN_EVCC*` 引用，若有任何引用在映射表中找不到对应项则直接
报错并不写入（避免留下部分修复的半成品）。

**验证**：修复后重跑 `final_verification.py`，39 项检查全部通过（此前为
38/39，仅"资源配对"检查失败）。

**教训**：
1. 处理"批量重命名+批量引用更新"时，若后续还会追加同类文件，重命名脚本本身的
   一次性运行不能保证覆盖后补内容——应在验收阶段做全量扫描兜底检查，而不是只信
   任重命名脚本"运行过一次就够了"
2. 安全备份文件（`*.before_*`）在问题被最终确认修复前不应被自动化脚本无差别清理

## 本项目遇到的问题

### 1. Res303 CNR 脚本与 Steam 引擎不兼容

**重要前提**：
- **Res303 补丁未经实际测试**：经验证，Res303 原版 Rio.arc 直接替换到游戏目录会崩溃
- **不能作为可靠参考**：虽然 Res303 声称"适用 Steam 版"，但其 CNR 脚本实际无法在 Steam 引擎上运行
- **可能的来源**：CNR 脚本可能从其他版本（PSV/PC 原版）直接复制，未经 Steam 版引擎适配

**问题描述**：
- Res303 补丁中的 12 个 CNR*.ws2 脚本在 Steam 版引擎上崩溃
- 经测试，Res303 原版 Rio.arc 直接替换到游戏目录也会崩溃
- CNR 脚本的指令格式与 Steam 版原生脚本存在多处差异

**技术细节**：
- CNR0005 的 byte 71-114 为 `0x46 Fbg01` 块，是首个导致引擎异常的指令
- Fbg01 块结构：`Fbg01\0 + 20字节参数(全零) + 0x65 0x64 + 后续参数`
- 该结构在原生 Steam 脚本中**完全不存在**（630次 `0x65 0x64` 都带有前置PNG文件名）
- 删除 Fbg01 块后的对话部分（byte 114+）也会崩溃，说明多处不兼容

**二分测试结果（CNR0005 前导部分）**：
- T0 (0字节前导) → 通过 ✅
- T1 (39字节：头+LAYER_ORDER) → 通过 ✅
- T2 (71字节：T1+变量设置) → 通过 ✅
- T2 + 立即跳转到 CCC0002 → 通过 ✅（临时方案）
- T2a (81字节：T2+Fbg01前10字节) → 黑屏但不崩溃 ⚠️
- T2b (91字节：T2+Fbg01前20字节) → ErrorLog "检测到文件终端" ❌
- T3 (114字节：T2+完整Fbg01) → 卡死+跳系统菜单 ❌
- T4 (160字节：T3+第一句对话) → 闪退 ❌

**格式修复测试结果**：
1. **修复 Fbg01 块的 byte[26] 字段** (`asset/Rio_cnr0005_fix_ed_to_e0.arc`)
   - 修复内容：将3个 Fbg01 块的 byte[26] 从 `0x64` 改为 `0x00`（对齐原生格式）
   - 结果：**依然闪退 ❌**

2. **修复 Fbg01 块的完整尾部参数** (`asset/Rio_cnr0005_fix_fbg01.arc`)
   - 修复内容：将3个 Fbg01 块的 byte[26:38]（12字节尾部）替换为原生最常见格式 `00 00 00 00 00 c0 3f 00 00 00 00 02`
   - 结果：**依然闪退 ❌**

3. **修复 charCN 通道码错误** (`asset/Rio_cnr0005_fix_char_cn.arc`)
   - 修复内容：将9处 `charCN\0`（6字符+null）替换为 `charYOU\0`（7字符+null），脚本长度增加9字节
   - 结果：**依然闪退 ❌**
   - 问题：长度变化可能破坏脚本内部的绝对偏移指针（类似 A Sky Full of Stars 项目中的 EVRET 偏移问题）

4. **删除所有 Fbg01 块** (`asset/Rio_cnr0005_remove_all_fbg01.arc`)
   - 修复内容：完全删除3个 Fbg01 块（共114字节），只保留前导初始化+对话内容
   - 结果：**依然闪退 ❌**
   - 说明：对话部分本身就有问题，不是 Fbg01 导致的

**详细技术分析**：

1. **Fbg01 指令格式差异**：
   - 原生脚本 Fbg01 短格式（marker=0x65）：
     - 结构：`Fbg01\0` + 20字节参数区 + `0x65` + 12字节尾部
     - 尾部12字节格式：`00 00 00 00 00 [浮点数4字节] 00 00 00 02`
     - 最常见的浮点值：1.5 (0xc0 0x3f 0x00 0x00), 1.0 (0x80 0x3f), 3.0 (0x40 0x40), 0.0 (0x00 0x00)
     - 统计：1955个原生 Fbg01 短格式样本，byte[26] 全部为 `0x00`
   - CNR0005 Fbg01 格式：
     - 尾部12字节：`64 00 00 00 00 3f 00 00 00 00 02 00`
     - byte[26] = `0x64`（原生全为 `0x00`）❌
     - byte[31-34] = `0x3f 0x00 0x00 0x00`（浮点值解析有误）❌
     - byte[37] = `0x00`（原生全为 `0x02`）❌
     - 这种格式在原生脚本中**从未出现过**

2. **charCN 通道码错误**：
   - 原生脚本语音通道码格式：`char` + 3字母角色代码（共7字符），如 `charYOU`, `charMIS`, `charTOU`
   - 统计：所有原生语音通道码都是7字符，共25种不同代码
   - CNR0005 使用：`charCN`（6字符），原生脚本中**从未使用过**
   - 根据语音文件名（`YOU025A5000.OGG` 等），正确的通道码应为 `charYOU`
   - 其他 CNR 脚本的错误映射：
     - `MSA` → 应为 `charMIS`（美沙 Misato）
     - `FYU` → 应为 `charTOU`（冬羽 Touko）
     - `KRI` → 应为 `charKIR`（桐璃 Kiri）
     - `MKI` → 应为 `charMIK`（美希 Miki）

3. **对话指令格式验证**：
   - `0x14` 对话指令结构与原生完全一致 ✅
   - 语音指令（`0x2e 0x28`）尾部结构与原生一致（`.OGG\0` 后15字节：`00 00 00 00 00 00 00 00 00 0a 00 00 65 00 00`）✅

4. **脚本长度与偏移问题**：
   - CNR0005 原始长度：3831 字节
   - 包含3个 Fbg01 块（offset 71, 679, 2425）
   - 包含9个 charCN 语音指令
   - 包含90个对话指令（`0x00 0x00 0x14`）
   - 修复 charCN 会增加9字节，可能破坏内部偏移指针

**根本原因分析**：

1. **CNR 脚本来源于非 Steam 版引擎**：
   - Res303 声称"适用 Steam 版"，但实际未经测试
   - CNR 脚本的多处格式（Fbg01、charCN）与 Steam 原生脚本完全不兼容
   - 可能从 PSV 版或 PC 原版直接复制，未做格式转换

2. **多重格式错误的叠加效应**：
   - 单独修复任何一个问题（Fbg01、charCN）都无法通过
   - 删除 Fbg01 后对话部分依然崩溃，说明问题不止一处
   - 可能需要同时修复多个格式错误，或存在其他未识别的不兼容点

3. **引擎指令完整性检查**：
   - T2b 测试显示，指令执行到一半会触发 ErrorLog "检测到文件终端"
   - 说明 AdvHD 引擎会检查指令的完整性，不支持截断的 stub
   - 任何修改都必须保持指令边界的完整性

**严格方法论重新验证 Fbg01 差异（同为 Steam WS2 格式对比）**：

之前"原生 WSC vs CNR0005"的二进制对比方法论有误（见下文第2节的更正说明）。改为**原生 WS2 脚本（如 CC0TOU 的 Fbg01 实例）vs CNR0005 的 Fbg01**，两者同指令集，逐字节对齐比较，确认了两处真实差异：
- byte[26]：原生 = `0x00`，CNR0005 = `0x64`
- byte[32]：原生 = `0x00`，CNR0005 = `0x3f`

5. **精确修复 v2**（`asset/Rio_cnr0005_fix_fbg01_v2.arc`）
   - 修复内容：仅将 byte[26] 和 byte[32] 改为 `0x00`（严格对齐原生对比样本），其余字节不动
   - 修复前先核实：之前的 `fix_fbg01`（第2项）虽然把 byte[26] 改对了，但同时把 byte[31:35] 写成了 `c0 3f 00 00`（浮点数1.5），导致 byte[32] 变成 `0x3f`——与本次找到的"byte[32] 应为 0x00"矛盾，说明那次修复引入了新的错误值，而非真正修复
   - 结果：**依然闪退 ❌**

6. **对话区二分测试（在已删除全部 Fbg01 的基础上）**（`asset/Rio_cnr0005_D1_pure_dialogue_only.arc` 等）
   - 背景：项 4（删除全部 Fbg01）已确认对话部分本身有问题，但从未针对纯对话区单独做二分定位
   - 用对话指令的自然边界（`0x00 0x00 0x14`）切分，定位到90个对话指令的起始偏移列表
   - **D1（前10句纯对话，无语音、无Fbg01，782字节）→ 依然闪退 ❌**
   - **关键发现**：连最简单的纯对话内容（不含任何语音/Fbg01/CG指令）都会导致崩溃，说明问题不在 Fbg01 参数、不在 charCN 通道码、也不在语音指令格式——这些此前怀疑的点都不是根本原因（或不是唯一原因）
   - D1 内容以 `char\0CN line 19%K%P\0\0` 结尾，末尾指令序列疑似不完整（缺少正常的收尾/跳转指令），需要进一步排查是否为"指令截断"问题（类似 T2b 测试中观察到的"检测到文件终端"现象）
   - **D2、D3 测试文件已生成但尚未测试**（`Rio_cnr0005_D2_with_first_voice.arc`、`Rio_cnr0005_D3_two_dialogues_after_voice.arc`）

**当前解决方案**：
- **临时方案（已验证）**：将所有 CNR 脚本替换成最小stub（前71字节 + 立即跳转回原目标），跳过H场景内容
- **完整方案（待实施，方向已调整）**：
  1. ~~逐指令对比原版和Steam版的格式差异~~ —— 已确认此路不通（原版WSC与Steam WS2指令集完全不同，见第2节）
  2. 需要在**纯对话区**内继续二分，缩小到具体哪几个字节/哪条指令触发崩溃（D1已确认782字节内必有问题，需要比D1更细的切分）
  3. 检查 D1 末尾指令是否被截断（对比原生脚本中同类对话指令序列的正常收尾方式）
  4. 或从头用 Steam 原生已验证可用的指令格式重写 H 场景对话内容

**经验教训**：
- **不能盲目信任第三方补丁**：即使 Res303 声称"适用Steam版"，也需要实测验证
- **二分测试法高效**：71字节的边界是通过二分法精确定位的，避免了盲目猜测
- **指令完整性很重要**：AdvHD 引擎会检查指令完整性，截断会导致ErrorLog
- **格式对齐是关键**：不同版本引擎的指令格式可能有细微差异，需要逐字节对比
- **对比必须同指令集**：跨格式（原版WSC vs Steam WS2）的二进制字节对比没有意义，即使字节位置能对齐、opcode数值巧合相同，语义也可能完全不同；必须用"同为目标格式"的样本互相对比（如原生WS2 vs CNR WS2）
- **不要过早收窄假设范围**：连续三次"修复Fbg01"均失败后，才通过对纯对话区做二分测试，发现问题实际独立于 Fbg01/charCN 之外存在；应在两次同类修复失败后就转向更基础的假设（如是否对话区本身有截断/格式问题），而不是持续在同一个假设方向上微调

### 2. 原版 WSC 解密算法破解（重大突破）

**来源**：从民间汉化组仓库 `cross-channel_chinese-localization_project/CrossChannel_Program` 的
`CrossChannelCrack.cpp` 中找到 `WSC_DecryptHelper`/`WSC_EncryptHelper` 函数实现。

**算法**：
```cpp
unsigned char WSC_DecryptHelper( unsigned char s ) {
    _asm { mov al, s; ror al, 2; mov s, al; }
    return s;
}
```
即**每字节循环右移2位**（`ror 2`），对应 Python：
```python
def decrypt(b):
    return ((b >> 2) | (b << 6)) & 0xff
```
加密（`WSC_EncryptHelper`）用 `rol 2`，是解密的逆操作。

**与 Steam WS2 的区别**：
- 原版 WSC：`ror 2`（循环右移2位）
- Steam WS2：`rol 6`（循环左移6位，见 `tool/ws2.py`）
- 两者混淆方式不同，指令集也完全不同（已在第 11 节确认）

**验证结果**：
用此算法解密原版 `Rio.arc` 中的 `CCC0000.WSC`（17814字节），Shift-JIS 解码后成功读出**完整的
日文剧本文本**，包括陽子（曜子）H场景的完整对话内容。关键验证点：
- 语音编号 `you012A5000`、`you025A5000` 等，与 Steam 版 CNR0005 中的 `YOU025A5000.OGG` 高度吻合
- CG调用顺序完全一致：原版 `EVCC0001` → `EVCC0002` → `EVCC0002B`，
  CNR0005 是 `BLACK.PNG` → `CN_EVCC0002.PNG` → `CN_EVCC0002B.PNG`
- 说话人、对话数量、场景结构均与 CNR0005 的占位符对话骨架一一对应

**重要限制**：
- 原版 WSC 与 Steam WS2 是**完全不同的指令集**，不能直接把原版的二进制指令结构套用到 Steam 版
- 例如原版 `0x46` 指令格式是 `0x46 + 8字节零 + "EVCC0002\0" + "hd\0d\0..."`（带文件名），
  而 CNR0005 的 `Fbg01` 指令是 `Fbg01\0 + 20字节参数 + 0x65 + 12字节尾部`（不带文件名）——
  两者仅 opcode 数值偶然相同，语义不同，无法互相参照

**这次突破的价值**：
1. **证实 Res303 转换的"骨架"是对的**：CNR0005 脚本的对话数量、说话人顺序、CG调用顺序、
   语音编号与原版完全对应，说明 Res303 确实是从原版正确提取了剧情内容
2. **缩小了问题范围**：崩溃不是因为"骨架错了"或"内容缺失"，而是 Res303 在把内容
   转换到 Steam WS2 格式时，某些指令的二进制编码细节出错（如 Fbg01 参数区、charCN 通道码）
3. **可作为翻译校对来源**：原版真实对话文本（当前 CNR 脚本中是占位符 `CN line N`）
   可以从这次解密结果中提取，用于后续真实文本还原（对应 `.lng` 文件）

**工具产出**：
- 解密脚本核心逻辑：`((b >> 2) | (b << 6)) & 0xff`
- 原版 Arc 解包规则见 `../CROSS_CHANNEL_Original/unpack_method.md`
- 解密后的 `CCC0000.WSC` 文本已保存到 `tmp/CCC0000_readable.txt`（临时文件，不提交）

### 3. CNR场景跳转指令格式Bug（已修复）

**问题描述**：Res303 的全部12个CNR场景(H场景)在进入后立即崩溃,表现为场景标题显示后Log窗口打开然后卡死。

**根本原因**：所有CNR场景的跳转指令使用了错误的格式:

```
错误格式: \x15\x00\x00\x16\x00\x00\x07<TARGET>\x00\xff\x00...
正确格式: \x15\x00\x00\x07<TARGET>\x00\xff\x08...
```

**技术细节**:
- `\x15\x00\x00`: 清除对话框指令
- `\x16\x00\x00`: 图层命令块起始标记(用于背景切换等)
- `\x07<TARGET>\x00`: 场景跳转指令
- `\xff\x08`: 正确的跳转标志字节
- `\xff\x00`: 错误的标志字节(导致引擎误解)

**崩溃机制**:
1. 引擎执行 `\x15\x00\x00` 清除对话框 ✓
2. 遇到 `\x16\x00\x00`,期待后续是图层操作指令(如 `\x64\x00\x33bg01\x00...`)
3. 但实际遇到 `\x07<TARGET>`,引擎将其误解为图层命令的参数字节
4. 加上 `\xff\x00` 错误标志,导致解析失败,场景卡死

**影响范围**: 全部12个CNR场景(CNR0001-CNR0008, CNR00009-CNR00011, CNR0105)

**修复方法**:
# 删除错误的 \x16\x00\x00 前缀,修正标志字节
错误: rb'\x16\x00\x00\x07([A-Z0-9_]+)\x00\xff\x00'
正确: rb'\x07\1\x00\xff\x08\x00\x00\x00\x00\x00\x00\x00'

**验证结果**: 修复后全部12个场景可正常进入,显示对话和CG,正常跳转回主线。

**调试方法论(关键教训)**:

1. **单变量对照实验**: 截断脚本但保留原文不变,隔离"截断位置"和"文本内容"两个变量,发现崩溃与文本无关
2. **二分查找临界点**: 在成功版本(2076字节)和失败版本(763字节)之间二分测试,发现即使只少21字节(96.9%保留)仍崩溃,引导检查最后的跳转指令块
3. **精确字节对比**: 对比原生脚本,发现跳转指令应该是13字节,而非我使用的16字节格式
4. **交叉验证影响范围**: 在326个原生脚本中验证标准模式,在Res303的12个CNR场景中发现100%都有相同错误,确认是系统性bug

**根因推测**: Res303使用的脚本转换工具错误地将 `\x16\x00\x00`(图层命令块起始)识别为跳转指令的标准前缀,可能是因为在分析原生脚本时,将背景切换块(`\x16\x00\x00\x64\x00\x33bg01...`)误认为是跳转前的固定序列。

**教训总结**:
- 不要猜测,要通过单变量实验验证
- 不要机械套用"看起来有效"的模板,要理解指令的语义
- 原生脚本是标准,任何偏离都需要验证
- 系统性错误需要系统性检查(12个场景100%错误 → 工具bug而非偶然)

详细的WS2指令格式说明见 `doc/file-formats.md` 的 "WS2 脚本格式" 章节。
