# 问题记录与经验教训

本文档记录 CROSS†CHANNEL 内容还原补丁项目中遇到的问题和经验教训。

## 从 A Sky Full of Stars 项目迁移的经验

### 1. Unicode 编码错误

**问题**：Windows 控制台默认 GBK/cp936，print 非 ASCII（✓/✗/中文）会 `UnicodeEncodeError` 中断脚本。

**解决方案**：
- 脚本开头加 `sys.stdout.reconfigure(encoding='utf-8')`（包在 try/except 里）
- 或统一用 `[OK]`/`[!]` 等 ASCII 标记

### 2. PNA 引用错配

**问题**：改写引用时使用简单字符串替换导致双前缀问题。

**错误示例**：
```python
# ❌ 错误做法
dec.replace('TCCT1000', 'ORG_TCCT1000')
```

这会命中已是 `ORG_TCCT1000` 名字的**尾巴**，把已改好的名再改一次 → 双前缀 `ORG_ORG_TCCT1000`。

**正确做法**：
```python
# ✅ 正确：用带 NUL 前缀的精确模式
dec.replace(b'\x00' + old_name, b'\x00' + new_name)
```

显示指令格式为 `<slot>\x00NAME.PNA\x00`，使用 NUL 前缀可以精确匹配。

**附加原则**：
- 每次运行时先检查"已满足则跳过"，保证脚本重复运行安全（幂等性）
- 改写后必须回读验证

### 3. 日文文件名识别

**问题**：脚本中带日文的资源名是 Shift-JIS 编码，不是 UTF-8。

**影响**：
- 搜索/改写资源引用必须用 `name.encode('shift_jis')` 构造字节模式
- 标准正则 `[A-Za-z0-9_]+` 匹配不到含日文的名字，审计时极易漏掉

**解决方案**：
```python
# 正确处理日文资源名
resource_name = 'TCCT1000'  # 如包含日文
byte_pattern = resource_name.encode('shift_jis')
```

### 4. 资源缺失卡死

**问题**：原版脚本引用了 Steam 已删除的背景/特效 PNG，引擎在硬载入时找不到文件，直接无响应（卡死），不弹任何错误码。

**症状**：
- `0x33` 硬载入缺失资源 → 卡死（无响应）
- `0x66` 遮罩缺失 → 容忍（静默跳过，仅画面瑕疵）

**解决方案**：从原版补入 Steam 已删的背景/特效 PNG。

**定位方法**（可复用）：
1. **台词 → 脚本偏移**：在 lng 中定位台词，再到解码后脚本里找到对应位置
2. **偏移 → 指令**：`ws2.decode()` 后按偏移解析紧随其后的 `0x33/0x34/0x66` 资源引用
3. **三方资源审计**：枚举脚本全部资源引用，逐一对 Steam 与原版目录求交集，筛出"仅原版存在"的资源

### 5. Arc 文件 Null Padding 导致哈希不一致

**问题**：某些 Arc 文件在表结束位置有 null padding（`\x00\x00`），位于表和数据段之间。`arcbuild.write_arc()` 不保留这个 padding，导致每次读写都产出不同的 SHA256，安装器哈希校验失败。

**症状**：
- 源文件 SHA256 ≠ 安装后文件 SHA256（相差 padding 字节数）
- 重复写入产生不同哈希（非幂等）
- 安装器验证失败

**解决方案**：
1. **规范化源文件**：运行一次 `arcbuild.normalize_arc_padding()` 去除 padding
2. **防护机制**：`arcbuild.verify()` 现已加入检查，如果发现 padding 会抛出错误
3. **确保幂等性**：规范化后，任何读写都产生相同哈希

**代码示例**：
```python
import arcbuild
from pathlib import Path

arc = Path('releases/Rio.arc')

# 规范化（去除 padding）
size = arcbuild.normalize_arc_padding(arc)
print('Normalized to {} bytes'.format(size))

# 验证（现已检查 padding）
cnt, fsize, end = arcbuild.verify(arc)
```

## CROSS†CHANNEL 特有的注意事项

### 6. 中文编码处理

**问题**：Shift-JIS 不支持中文字符，lng 文件可能使用 UTF-16 或其他编码。

**注意事项**：
- **脚本内容**（资源名）使用 **Shift-JIS** 编码
- **中文字符不能用 Shift-JIS 编码**，会抛出 `UnicodeEncodeError`
- lng 文件中的中文文本编码方式待确认

**搜索/匹配脚本内容时**：
- 日文文本：`text.encode('shift_jis')`
- 中文文本：可能在 lng 文件中，不在 ws2 脚本中

### 7. LNG 格式未知

**问题**：lng 文件格式未公开文档，需要逆向分析。

**当前状态**：
- 已知使用 rot6 混淆（与 ws2 相同）
- 包含文本偏移表和替换文本
- 具体结构待分析

**解决方案**：
1. 分析 Res 303 的 lng 文件样本
2. 对比 ws2 和 lng 的文本对应关系
3. 使用十六进制编辑器查找模式
4. 开发读写工具（如需）

### 8. 分支复杂度

**问题**：CROSS†CHANNEL 的分支数量可能很多（从脚本命名看，有 A/B/C/D 等多分支）。

**挑战**：
- 建立完整的分支树
- 标识每个分支的 H 场景位置
- 逐一处理每个分支的调用链

**解决方案**：
- 使用工具自动分析调用链
- 建立分支映射表
- 分阶段处理（先主线，后分支）

### 9. 资源命名差异

**问题**：CROSS†CHANNEL 的资源命名规则与 A Sky Full of Stars 不同。

**差异**：
- 立绘：`T{角色代码}{分类}{编号}{变体}.pna`（如 `TCCT1000.pna`）
- 事件 CG：可能使用 PNG 格式，位于 Chip1/Chip2.arc
- 无明显的路线代码（COM/HIK/SAY 等）

**注意事项**：
- 不能直接套用 A Sky Full of Stars 的命名规则
- 需要重新分析资源命名模式
- 建立新的命名映射表

### 10. ev 槽特性未知

**问题**：CROSS†CHANNEL 只有单个 `ev` 槽，与 A Sky Full of Stars 的 `ev01/ev02` 双槽不同。

**未确认**：
- ev 槽是否有 7 字节 stem 硬限制
- ev 槽对 `ORG_` 前缀的容忍度
- 事件 CG 是否使用 ev 槽（Steam 版脚本中未发现 ev 槽引用）

**解决方案**：
- 实测验证 ev 槽特性
- 参考 Res 303 的方案
- 如不使用 ev 槽，可能无此问题

## 最佳实践

### 脚本改写原则

1. **精确匹配**：使用显示指令上下文（带 NUL 前缀）进行替换
2. **幂等性**：脚本必须可重复运行，每次检查"已满足则跳过"
3. **回读校验**：改写后必须回读验证，确认修改成功
4. **编码正确**：日文资源名使用 Shift-JIS 编码

### 验证清单

改写脚本后必须执行：

- [ ] 调用链完整性检查
- [ ] 资源配对验证（`*_h` ↔ `ORG_*`，`*_en` ↔ Steam 资源）
- [ ] 资源存在性验证（所有引用的资源都存在）
- [ ] 冗余检测（无重复脚本、无未使用的 ORG_* 资源）
- [ ] Arc 文件规范化检查（运行 `arcbuild.verify()` 检测 null padding）
- [ ] SHA256 校验稳定性（修改后重新读写一遍，验证 SHA256 保持一致）

### 调试技巧

1. **遇到卡死无响应**：
   - 定位最后一句台词的位置
   - 检查紧随其后的 `0x33` 资源引用
   - 验证该资源是否存在

2. **遇到渲染失败或崩溃**：
   - 检查是否存在同名 PNA 冲突
   - 检查请求的 layer_id 是否超出 layer_count

3. **场景结束后流程异常**：
   - 检查跳转目标是否正确
   - 检查后缀是否一致

4. **文本显示异常**：
   - 检查 lng 文件是否存在
   - 检查字体文件是否支持汉字
   - 检查文本编码是否正确

5. **安装器哈希校验失败**：
   - 源 Arc 文件可能存在 null padding
   - 运行 `arcbuild.verify(path)` 检测是否有 padding
   - 规范化命令：`arcbuild.normalize_arc_padding(path)`

## 经验总结

### 从 A Sky Full of Stars 学到的

1. **命名空间隔离是核心**：ORG_ 前缀或其他方案隔离两套资源
2. **幂等性是必须的**：所有改写脚本必须支持重复运行
3. **回读校验是保障**：改写后必须验证，不能假设成功
4. **实测优于逆向**：对于引擎特性，A/B 测试比纯静态分析更高效
5. **文档是资产**：详细记录每个问题和解决方案，避免重复踩坑

### CROSS†CHANNEL 特有的

1. **复用已有方案**：Res 303 已验证可行，优先复用其资源和方案
2. **渐进式实施**：从简单场景开始，逐步扩展到复杂分支
3. **工具先行**：开发自动化工具分析调用链和资源冲突
4. **分阶段验证**：每完成一个阶段立即验证，不等到最后
