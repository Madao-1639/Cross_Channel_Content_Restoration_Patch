# 问题记录与经验教训

本文档记录本项目遇到的问题、定位方法与结论。**章节编号即其他文档的引用锚点**（`§N`）。

---

## 一、通用方法论

### 1. 精确匹配、幂等性、回读校验

- **改写资源引用必须用显示指令上下文精确替换**：指令格式是 `<slot>\x00NAME.PNA\x00`，
  简单字符串替换会命中已改名文件的尾巴 → 双前缀（`TCCT1001` 被再改一次）。
  正确做法是 `dec.replace(b'\x00' + old_name, b'\x00' + new_name)`。
- **所有工具脚本必须幂等**：运行前检查「已满足则跳过」，改写后回读验证，不假设成功。
- **不要在调用点绕过工具层缺陷**：归档写入对已存在的大文件做 `O_TRUNC` 会稳定失败，
  修在 `tool/arcbuild.py` 的 `write_arc`（改为「临时文件 + `os.replace`」原子写入）
  才是一次性解决。

### 2. 「字节 100% 覆盖」不构成正确性证明

反汇编器只要能在**错误的位置重新同步**，覆盖率检查照样通过 —— 早期把 `28`/`1e` 的尾段
少读 12/7 字节就是这样被掩盖的（尾段余下的字节恰好能解析成合法指令）。

- **自带发射器 + 自带解析器互相验证是循环论证**。能打破循环的只有第二实现或原生语料统计。
  本项目的判据是原生语料的**位置直方图**（独立于两个实现）。
- **凡定长尾段/定长参数块，都要按全语料的逐字节模态核对**，不是只看覆盖率（见 7.）。
- **错误会被对称复制**：文档里写错的字节模板，会被下游实现原样继承 ——
  Res303 侧的转换器正是从本文档早期写法抄了 `34 73 st01`（产出 `sst01`）与 `65 64 00 00`，
  且它自己的 27 项回归测试全部通过（因为它的发射器与解析器同样对称）。

### 3. 先找同引擎的官方样本

「实测优先」之前先问一句：**这个机制在同引擎的别的游戏里长什么样**。

- 名字替换表的规则是从 A Sky Full of Stars 的**官方简中包**对照出来的（见 9.），
  比在 CROSS†CHANNEL 上逐个试编码又快又确定。
- 前提是找到一份**未加密的同引擎 exe**：CC 自己的 `.text` 段是加密的，而 ASF
  仅差 0.01 版本且为明文，结论可直接外推。
- 但逆向在有明文样本时也别放弃：本项目的「脚本内窄字节 = CP932」（见 10.）与
  「表键必须等于脚本标记」两条关键结论都是静态分析拿到的，比逐个试快且确定。

### 4. 偏移假设必须用全区间扫描排除

「我记得应该从这句开始」这类主观判断在拼接脚本时不可靠；**局部匹配不是证据**——
即使前几条文本看起来对应正确，也可能是偏移错误下的巧合。

做法：**对每个候选偏移做全量比对**，只有真实偏移能让全部条目零误差。
（实例：定接缝用的 CCS 基准行号，在若干候选偏移中只有一个是让全部 169 条零误差的解。）

### 5. 不能盲信第三方产物，也不能盲信外部复审

- **Res303 的补丁未经 Steam 版测试**：把它原版的 `Rio.arc` 直接覆盖到游戏目录会崩溃，
  其还原脚本的指令格式与 Steam 引擎多处不兼容（`Fbg01` 参数区、`charCN` 通道码、
  跳转标志字节……）。**声称「适用 Steam 版」不等于能跑，必须实测。**
- **外部复审的正确用法是「提出假设」，验证仍要回语料**：对照外部实现（Res303 侧基于
  本文档做过一版 WSC→WS2 实现并回传）时，本轮 4 条采纳、4 条驳回，全部以全语料统计为准，
  没有整体接受或整体否定。
- **不要过早收窄假设范围**：连续三次「修 Fbg01」均失败后，才对纯对话区做二分测试，
  发现问题独立于 Fbg01 之外存在。应在两次同类修复失败后就转向更基础的假设。
- **报告结论必须独立复算**（本地重建 + 逐字节比对），不直接采信第三方报告的状态码。

## 二、格式与引擎机制

### 6. Arc null padding 导致哈希不一致

某些 Arc 文件在**表结束位置与数据段之间**有 null padding（`\x00\x00`）。
`arcbuild.write_arc()` 不保留它，于是每次读写产出不同的 SHA256，安装器校验失败。

- **规范化**：`arcbuild.normalize_arc_padding(path)` 去一次即可；
- **防护**：`arcbuild.verify()` 会检测 padding 并拒绝；发现 padding 即跑规范化；
- 规范化后哈希稳定，重复读写产生相同字节序列。

### 7. 定长尾段必须按整条指令读

`28`(SE) 与 `1e`(BGM) 的尾段实际是 **22 / 17 字节**，不是 10 ——
少读之后余下的字节（`0a` 7B + `01` 5B）**恰好**是合法指令序列，解析器在错误位置重新同步了。
发射端的后果更严重：写出去的 `28` 比原生少 12 字节，引擎会把后续指令吃进参数里。

**判据是位置直方图，不是「能解析出来」**：若尾段只有 10 字节，则第 10–21 字节应是
「下一条指令」，实际却有 1467/1556 条在同一位置是 `0x0a`、其后 11 个位置几乎恒为 0 ——
不存在这种指令。

同一规律也适用于**语音**指令：`2e 28` 的尾段是 22 字节，短于此会让引擎读入下一条指令的
头部，**指令边界错位 = Runtime Error**。布局与全语料不变量见
[wsc_to_ws2_conversion.md](wsc_to_ws2_conversion.md) 3..6。

> 用户报告的崩溃位置可能有误导性：报告「在对话 18 崩溃」，实际崩在对话 18 **之后**的
> 语音指令解析上（`%K%P` 等待点击，所以看起来是"点击后崩溃"）。

### 8. `14` 的 id 与 `0f` 的 strid 是同一个字符串池

两者属于同一个**按文件出现顺序**填充的字符串池，**选项文本也占槽位**，
所以选项之后的对话 id 会**跳过**被占用的号。

证据（全语料，非单样本）：

- `strid == 表前 0x14 条数` 命中 50/55；5 处偏差正好等于更早的选项文本占号数。
- 原生 `CCA0006`：204 句对话 id `0..203` → 选项 strid `204,205,206` → 下一句 id `207`；
  WSC 侧的 id 序列与之逐项相同。
- 同名对同规则：`CCA0004`（WSC 145 句 → sid `145,146`；Steam 151 句 → strid `151,152`）、
  `CCD0102_EN`（2 句 → `2,3,4,5`）。
- 转换产出 43 个含选项脚本，strid 与 WSC `sid` **逐表逐项相等**。

**教训**：id 不是自由标签，是与池绑定的一条不变量。给「看起来没人用」的字段随手填
0 基序号（如把 strid 写成表内下标）会破坏它，而破坏只会在选项文本错位时暴露。

### 9. 名字替换表 `NameTable.txt`：表键必须等于脚本里的标记

**症状**：正文与选项都已汉化，唯独说话人名字框始终显示英文。

**此前的误判**：一度认定这是「`%LC` 用什么字节编码」的问题 —— 因为
`15 %LC<Taichi> 00 00` 里的名字是**脚本内的原始字节**、不经 lng 替换，而简体专用字
（见/雾/贵/樱/游/纱/师/长/丰/咪）不在 CP932 里。**这个观察没错，但由此推出「必须改字节」
是错的** —— 漏掉了引擎在字节之外还套了一层替换表。

**根因**：引擎拿脚本里的 `%LC<英文名>` 去查 `Rio.arc` 里的 `NameTable.txt`（UTF-16LE），
命中就替换成表右列。Res 303 确实放了这张表，73 行**内容完全正确**（与脚本 73 个 `%LC`
名字一一对应、零偏差，中文还是简体），**但键前缀被写成 `%LR`**，与脚本的 `%LC` 对不上 ——
引擎查不到，于是原样显示英文。

**判定依据**（对照 A Sky Full of Stars 的官方简中包）：

| 游戏 | 脚本里的标记 | 表键前缀 | 表键 vs 脚本名 | 结果 |
|---|---|---|---|---|
| ASF | `%LF`（26,130 处） | `%LF`（140 行） | 一一对应，「只在表里」0 个 | ✅ 生效 |
| CC | `%LC`（27,132 处） | `%LR` → 修正为 `%LC`（73 行） | 一一对应，「只在表里」0 个 | 修正前 ❌ |

`%LC` / `%LF` / `%LR` 都是 `AdvHD.exe` 命令标记表里的合法标记，**每个游戏用哪个字母由
脚本生成时固定，与语言切换无关**（ASF 的英文版和简中版都用 `%LF`），所以表键必须跟着
脚本走。

**修正**：`script/fix_nametable_prefix.py`（行首与制表符后的 `%LR` → `%LC`，共 146 处；
备份 + 回读校验 + 幂等）。**不改 ws2、不动偏移、不涉及任何编码转换。**

**教训**：名字表是个 `.txt` 成员，混在 300+ 个 `.ws2` 里毫不起眼；三个字母长得又像，
没有对照样本时无从判断哪个才对 —— 见 3.。

### 10. 文本编码路径：脚本内窄字节 = CP932

`AdvHD.exe` 内建 BIG5 / GB2312 / SHIFTJIS / UTF-8 四种代码页。对 ASF 的引擎（明文，可反汇编）
统计 `MultiByteToWideChar` 的调用点参数：

| 代码页 | 出现次数 |
|---|---|
| **CP932（Shift-JIS）** | **40** |
| 参数在寄存器中（未能静态解析） | 9 |
| UTF-8 (65001) | 2 |
| CP_ACP | 2 |

反方向的 `WideCharToMultiByte` 以 UTF-8 为主（4 处）—— 那是**输出**方向，用于把宽字符交给
Lua / Steam API。**引擎内部用 CP932，Lua 层用 UTF-8，跨层时显式转换**
（`MyConv__lua_utf8tosjis` 等绑定即为此存在）。

**结论**：`%LC` 这类**脚本内窄字节**受 CP932 限制，简体专用字写不进去。
**文本汉化必须走宽字符通路** —— 正文/选项走 `.lng`（UTF-16LE），人名走
`NameTable.txt`（UTF-16LE）。这也是官方简中的做法。

### 11. 原版引擎与 Steam 版不兼容（WSC vs WS2）

起初假设原版游戏（民间汉化版）可作为 Steam 版缺失资源的补充来源。分析后确认两者是
**完全不同的引擎实现**：

| 特性 | 原版 `CROSSCHANNEL.exe` | Steam 版 `AdvHD.exe` |
|---|---|---|
| 脚本格式 | `WSC`（无 rot6 混淆，纯二进制） | `WS2`（rot6 混淆） |
| 立绘格式 | 未见 PNA，走 `ANM`/`MSK` 等分类 tag | PNA 图层 |
| 特征字符串 | 无 `AdvHD`/`WS2`/`PNA`/`lua` | 有 `PNA`/`lua` |
| 版权声明 | WillPlus / CROSSCHANNEL Co., Ltd. | MoeNovel（Amaneko 系） |

原版 Arc 归档格式（**非本项目使用格式**）：表项为固定 21 字节/条
（`13s name(null-padded)` + `u32 size` + `u32 rel_offset`），与 Steam 版的 UTF-16LE
变长名字完全不通用。

**影响**：不能把原版的 `Rio.arc` / `Chip.arc` / `Voice.arc` 解包后直接塞进 Steam 版，
「从原版补入资源」在**二进制层面**不可行。

**但内容层面完全可用**（本项目实际依赖的四条）：

1. **WSC 解密**：算法是每字节循环右移 2 位（`ror 2`，来源：民间汉化组仓库
   `CrossChannelCrack.cpp` 的 `WSC_DecryptHelper`），Python 即
   `((b >> 2) | (b << 6)) & 0xff`。加密用 `rol 2`。
   **这是内容还原的起点** —— 解密后可读出完整原版日文剧本。
2. **资源引用与插入位置**：指令集不兼容仅限二进制格式层面；解密原版 WSC 后，每个脚本
   引用了哪些文本、在什么位置插入 CG/语音/背景，与 Steam 版一一对应，可作为权威信源。
3. **语音资源**：原版 `Voice.arc` 里的 OGG 可直接补入 Steam 版
   （`script/import_missing_voices.py`）。
4. **场景编号验证**：原版脚本清单可用于核对还原点是否覆盖了原版对应的全部场景。

> **授权提醒**：`CROSS_CHANNEL_Original/readme.txt` 声明未经允许不得破解分析。
> 本项目只做**只读结构分析**（识别脚本/资源对应关系以支持内容还原），
> 未逆向或再分发汉化组的破解手段本身。

## 三、资源

### 12. Chip2 事件 CG 的前缀白名单

**症状**：场景背景一直黑屏，即使引用的 CG 文件确实存在于 `Chip2.arc` 中。

**根因**：Steam 版引擎对 `Chip2.arc` 的事件 CG 实施**前缀白名单**，只认可 `EVCC` 开头的
文件；其他前缀（如 `CN_EVCC`）被**完全忽略 —— 不报错、不加载**。

**规则**：还原 CG 一律命名 `EVCC9XXX[变体].PNG` 并放进 `Chip2.arc`（编号规则见 14.）。

**经验**：

1. 引擎可能对特定资源类型实施**命名白名单**，不仅限于槽位前缀；
2. **白名单违规不报错**，只是静默忽略，导致排查困难；
3. 命名规范应遵循 Steam 原版模式，避免自创前缀；
4. 测试时必须验证资源**实际加载**，不能只检查文件存在性。

### 13. 资源缺失的引擎行为与定位方法

- **`0x33` 硬载入缺失资源 → 卡死（无响应）**，不弹错误码。转换产物入包前必须消掉
  `missing_resources` 清单。
- **`0x66` 遮罩缺失 → 容忍**（静默跳过，仅画面瑕疵），不会崩溃。

**定位方法**（可复用）：① 在 lng 中定位台词 → 在解码后脚本里找到对应偏移；
② 按偏移解析紧随其后的 `0x33`/`0x34`/`0x66` 资源引用；
③ 枚举脚本全部资源引用，与 Steam 原版归档求交集，筛出「仅原版存在」的资源。

### 14. 还原 CG 的命名、归档与编号

1. **前缀一律 `EVCC`**（见 12.）。
2. **归档**：事件 CG 进 `Chip2.arc`，背景进 `Chip1.arc`，立绘进 `Graphic.arc`。
   `asset/Graphic.arc` 现与 Steam 原档逐字节相同，**不再分发**。
3. **编号一律落在 `EVCC9XXX` 段，按「基号 + 脚本引用顺序」分配**：按剧情顺序扫描脚本，
   首次被引用的「基号」拿 `9000`，其后递增；同一张 CG 的差分共用一个编号，只用变体字母区分。
   37 个文件 → 19 个编号 `EVCC9000`–`EVCC9018`。
4. **原版系统图 `SGCC0020`**（原版 `CCB2101.WSC` 以 `0x48`/`0x46` 引用）与 Steam 的
   `sgcc0020.png` 同名但内容不同，按同名冲突规则并入 `EVCC9004`。

实现：`script/renumber_evcc9xxx.py`（幂等；基号由**内容哈希**查表，与文件名无关）。
对照用 `python script/renumber_evcc9xxx.py --check`（只打印、不写入）。

**教训**：

1. **「已按规则处理」必须全量核验，不能抽样**：36 个改对了不等于第 37 个也对，
   一条扫全档案的 `CN_` 前缀检查就能发现。
2. **规则要能自检**：「引用序列是否递增、同一编号的文件是否同基号」是可自动化的验收断言
   （`script/final_verification.py`）。同理 Chip2 的每个成员都必须带 PNG 签名
   （曾混入 2 个 MOS 冒充 PNG 的无引用成员，已由 `script/remove_unreferenced_mos.py` 清除）。

### 15. CG 差异判定：同名 ≠ 内容审查

**对比对象**：Steam 侧取 `backup/Chip1.arc` + `backup/Chip2.arc` + `backup/Graphic.arc`，
原版侧取 `../CROSS_CHANNEL_Original/` 的 `Chip.arc` / `Chip_B` / `Chip_E` / `Chip_I` /
`Chip_S` / `Chip_T`（老式归档，`arcbuild.read_old_arc` 可读），**按同名配对**比较。

| 类别 | 数量 | 说明 |
|---|---:|---|
| 同名图片 | 232 | 其中 **189 对浑浊像素占比 <1%**、8 对 1–5%、0 对 5–10%、34 对 >10% |
| Steam 独有 | 852 | 大头是立绘 `TC**` 与 119 个 `EVCC*` |
| 原版独有 | 520 | 本项目补入的 37 张即出自这里的 36 个 `EVCC*` + `SGCC0020` |

**结论：同名不等于内容审查，当前没有任何一例被确认。**

那 34 对 >10% 的**全部是系统图**，且**全部是「同名不同物」**：原版 `Chip_S.arc`/`Chip_E.arc`
里装的是小尺寸 UI 元件（`SGCC0017` 352×456、`SGCC0010` 608×458…），而 Steam 的
`Graphic.arc` 里是 1280×720 整屏 —— 名字沿用了，内容不是一回事。

还原关心的 `EVCC*` 事件 CG 里差异最大的两个：

| 图 | 强制拉伸比较 | **保宽高比 + 最优对齐后** | 尺寸（Steam / 原版） | 结论 |
|---|---:|---:|---|---|
| `EVCC0009` | 9.6% | **3.85%**（8×6 网格差全部 0–1/255） | 1280×917 / 800×600 | **同一张图** |
| `EVCC0023B` | 30.6% | 42.8% | 1280×734 / 800×600 | 整幅不同，无局部涂改特征 |

⚠️ **「相似度 > 60% 即为内容审查」的判据是反的**：高相似恰恰说明是同一张图；而**局部审查**
（一小块遮挡/涂改）在全局相似度上几乎看不出来（改 5% 像素，相似度仍有 95%）。
另一类假差异来自**把原版图强行拉伸到 Steam 尺寸**（宽高比 1.396 / 1.744 vs 1.333 会凭空
产生大片差异）。可行判据三条并用：① 同名；② **保宽高比 + 最优对齐后的分块局部差异**；
③ 脚本层证据 —— 原版该场景引用了它、且 Steam 同名文件画面不同。

**旁证**：Steam 独有的 119 个 `EVCC*` 与原版做全对全匹配，只有 4 个相似度 ≥95%
（都是与 `BGCC0000` 等背景图的重合），基本可判定为**新增 CG**。
37 个还原文件与原版同名图相似度 100% / 92–100%，证实 Res303 的 `CN_EVCC*` 就是原版图
（升采样到 1280×960），`BASE_OF_SHA` 靠内容哈希反查出的基号是**正确**的。

### 16. 姊妹场景：同一段剧情在两章里各有一份脚本

原版把**同一段剧情**在 A 章和 B 章各存一份脚本，两份几乎逐字相同。这不是冗余，
是作品结构（同一周的事件在不同角色线重复发生）。

**实例 `CCA0025C` ↔ `CCB1014C`**（見里的 H 场景）：

| 维度 | 两边的情况 |
|---|---|
| 说话人 | 都是 見里 184 句 + 太一 112 句 |
| 语音 | **同一套文件**：`MSA000B1101`…`MSA183B1101`（各 184 条，同名同内容） |
| 事件 CG | 同一套：`EVCC0012` / `EVCC0013` / `EVCC0013A` |
| 台本 | 572 / 571 行，去掉 ruby 注音后 **569 行逐字相同（99%）**，difflib 0.996 |
| **仅有的差异** | ① 行 353/354：A 拆成两句，B 用 `\n` 合并成一句；② 行 361：A `思いだしたように`，B `もいだしたように` |

**这是系统性的**：全原版语料扫出 **26 对**姊妹场景，编号规律 `CCA00nn` ↔ `CCB10(nn-9)`，
其中 `CCA0010`/`CCB1001` 与 `CCA0021`/`CCB1010` 是 **difflib 1.000、零差异**。
`CCB1101` 是 `CCA0025C`/`CCB1014C` 的第三个副本。

**影响**：

1. **「这句话属于哪个脚本」的投票法在姊妹对上失效** —— 两场台本本来就 99% 相同，
   这是方法的分辨极限，不能据此断定内容搬错。
2. **`Rio.arc` 里那 2 组内容相同的 `.lng` 由此解释**（`CCA0005B_en.lng` = `CCB0004B_en.lng`
   等）——对应 ws2 文本逐行相同，lng 自然相同。不是引入的冗余，也不能合并（服务不同分支）。
3. 姊妹对**各自都要还原、不能合并**：两者都可正常到达（前一个脚本的选项表 `0f` 各有一条
   指向它们）。

## 四、调用链

### 17. 原版内容分散在多个脚本里

**判断「漏没漏」要看整条链，不能只看某个脚本的覆盖率**。原版一个场景的内容会分散在
宿主、后继脚本、姊妹场景里；只看一处会得出「6 个场景没还原完」的错误结论。

**反向信号更可靠**：**宿主同时覆盖前段与后段**，说明它承载的是**整场删节版**，
而不是「还原段之前的那一段」——这正是接缝要处理的对象（见 18.）。

**对位有噪声底，判缺口要看数量级**：与源 CCS 做中文对位时，**已知正确**的场景实测仍有
约 8 行对不上（来自 Steam 对删节段的改写）。

- **0–8 行 = 噪声**，不是缺口；
- **几十上百行、且呈尾部大段连续**才是真缺口；
- 对位**只能用显示文本** —— 语音名 / 立绘名 / 背景名三个结构锚点实测全部不可用
  （Steam 侧语音按角色全局重编、立绘被重编、背景与 CG 会被替换重排）。

### 18. 接缝错位：宿主播完删节版才进还原脚本 → 改为「就地插入」

**症状**：本应切到 H 场景的位置，却先播出一串不连续片段、还混入本场景没有的文本
（「理想。」），之后才进还原脚本；表现为台词重复、错乱。

**根因**：Steam 删除 H 场景时，会在宿主脚本尾部保留该场景的**删节版**（把原版几十句压成
几句）。旧接缝把还原脚本追加在宿主脚本全部文本之后，而宿主的删节版是**按序跑完整场**的，
所以它播完之后再进还原脚本，完整版就出现在「结尾之后」——
**不是「整段播两遍」，而是顺序倒置 + 局部重复**。这不是 Res303 额外塞进去的内容，
Steam 原生脚本本身就是那样。

**定案做法：把原版内容就地插入调用脚本，不再引入还原脚本。**

```
宿主脚本 = [前段：Steam 原生，源 0 .. 接缝]
         + [插入段：源 WSC 的删除区间转换后就地插入]
         + [出口尾段：Steam 原档「末句对话之后」的字节，含原出口]
```

- **不再有 `CNR###` 脚本、不再有额外跳转、不删除 Steam 内容**；12 个宿主全部就地插入。
- 判据与逐场景参数见 [call-chain.md](call-chain.md)「就地插入接线」；
  `script/audit_inline.py` 是回归守卫（「恰好一次、无缺失、无重复、无倒序」）。
- `CCC0000` 试点**实机验证通过**。

**为什么必须整段搬而不是只搬对话**：原版还原区间里有大量演出指令
（立绘 / 等待 / BGM / 蒙版 / 时序），宿主侧的删节版里也有（`CCD4003A` 183 条、
`CCD1001B` 116 条……）；旧做法**截断宿主**就会把宿主承担的演出一并丢掉，
表现为掉立绘、掉 BGM。**不能单独做接缝截断** —— 就地插入天然避免了这个问题。

**被丢弃的非源内容**：`CCC0000_en` 尾部有 1 条 `Ideal.` / `理想。`，只出现在 Steam 宿主里，
汉化组 CCS 与原版 WSC 都没有它。按「缺少的信息不应猜测补全」，随被替换的删减段一并丢弃。
其余场景的宿主也各有少量对不上源序列的台词（`CCB2013_en` 20 条、`CCB2101_en` 10 条），
多数是 Steam 对删节段的改写。

### 19. 就地插入接线的技术要点

**① 12 个宿主的指令集里没有任何绝对偏移**

`06`（文件内跳转）/ `01`（`mode=0x85` var 条件）/ `0f`（选项表）**全部为 0**，
所以把外部指令流插进宿主中间不会让任何指针失效。唯一例外是 `CCC0000_en` 的
`01 mode=0x85` —— 它不在正文里，而在**出口尾段**，第二出口的 `b` 字段要按新布局重算
（`script/splice_restoration.py` 已处理并回读校验）。

**② `14` 的 id 必须等于「字符串池出现序」**

全语料 363 个原生脚本里 354 个满足 `id == 0..n-1`；**9 个反例全部是有 `0f` 选项表的脚本**
（选项文本占池槽位）。所以：

- 就地插入时，插入段首句的 `id` 必须等于**前段保留下来的对话数**（`ConvertOptions.pool_start`）；
- 截掉脚本头部后（`CCD5001B` 从源 1112 起），剩下的 `14` 必须**整体重编号**成 `0..n-1`。

**③ 宿主「第一句对话之前」是场景开场件，必须原样保留**

插入段里没有这些，因为它们来自 Steam 而不是源 WSC：`CCB2101_en` 的
`载图 SGCC0020.PNG` + `0b id=1233/1482`（鉴赏钩子）、`CCC0000_en` 的 `SCENETITLE004.PNG`、
`CCD5001A_en` 的 `SCENETITLE011.PNG`。源 WSC 对应位置是 `0xe0` 章节标题，转换器会跳过它，
覆盖掉就丢了。⇒ **插入点一律落在第一句对话之前的那个 `15` 上**。

**④ 切片转换（`tool/wsc2ws2.convert_range` + `slice_mode`）**

接在宿主中间与做成独立脚本有三处不同，都靠 `slice_mode` 处理：出口**不写**（由宿主的出口
尾段承担）、文尾 `0a`（停 BGM）**照常发射**、开头 `16 01 00`（开对话框）**抑制**、
字符串池从 `pool_start` 起。

**⑤ 插入段终点不能一律取到 `ff`**

`hi` 是场景末句时，终点取该句之后、`ff` 之前的场景末尾事件（等待 / 停 BGM）；
`hi` 是**交接点**时（场景在本脚本之后还有内容，如 `CCD1001B`、`CCD5001A`），
终点只能取到该句末尾——否则会一路吞到文件尾、把后继脚本的内容也搬进来
（实测这两个场景曾因此多带 700 / 349 句）。

**⑥ 资源重命名：内容哈希 + 命名规则，不手抄**

- **事件 CG**：原版基号 → 当前 `EVCC9XXX` 编号。用 `asset/Chip2.arc` 里每个 `EVCC9xxx`
  文件的**内容哈希**查 `BASE_OF_SHA` 反推基号（与 `script/renumber_evcc9xxx.py` 同源）；
  变体字母原样保留（`EVCC0002B` → `EVCC9005B`）。
- **立绘**：规则 `TC{角色}0{nnn}{变体}` → `TC{角色}1{nnn}{变体}`。两版立绘被重编过
  （原版 `TCMM0002C` ↔ Steam `TCMM1001C`），且原版是 `.PNG`+`.MSK`、Steam 是 `.PNA`。
  还原区间的 46 个立绘引用里按此规则**两侧都存在 44 个**，余下 2 个非立绘
  （`SGCC0020` 并入 `EVCC9004`，`EFCC0003` 保持原名）。
- **不要照抄原版 WSC 名** —— 两版资源被重编过，照抄会引用不到。
- 工具 `script/build_rename_map.py`：规则解不掉的条目**单独列出，不许静默跳过**。

**⑦ 扩覆盖范围要补资源**

把还原段扩到交接点之后，新覆盖的几百句会引用补丁里还没有的资源。已补入 **186 条语音**
（`script/import_missing_voices.py`，源 `../CROSS_CHANNEL_Original/Voice.arc`，
32230 → 32416 成员，+16.2 MB）。关于 `.soundlevel`：原版 `Voice.arc` 只有 `.OGG`
（无包络），Steam 侧才带 `.soundlevel`。**无包络的 OGG 照样播**（`YOU035A5000`…`YOU042A5000`
这 8 条就是无包络补入的，实机验证通过时正常播放），所以只补 OGG，不凭空造包络。

**⑧ 渐变时长：原版 WSC 里没有这个数据（已穷尽排查）**

转换器对源里没有 `22` 的转场统一用 `default_fade = 1.0`。**原版 WSC 没有逐次渐变时长** ——
把 324 个源脚本里**每个 opcode 的每个数值字段**的取值集合与渐变候选集
（300/500/1000/1500/3000ms）比对，命中的只有 `0x4a.b`（**等待**语义，已映射为 `11 timer01`）、
`0x22.b`（恒定 500，是"这次淡入 500ms"的开关，不是逐次参数）、以及 `0x68`/`0x65` 的
几何量（矩形坐标）。`0x65`/`0x68`/`0x69` 是文本框/效果矩形，不是渐变；`0x47`/`0x49` 是标志位。

⇒ **源里没写 `22` 时的默认渐变时长由引擎决定，WSC 未记录。** 三个转换器各选了各的默认值：
Steam（MoeNovel）用 0.3/1.5/3.0 等（不是从源里读的）、Res303 统一 0.5、本项目统一 1.0。
旁证：`CCC0000` 源里只有 2 处 `22`，而 **Steam 自己的宿主在那 4 处转场用的正是 1.0**。
按项目约定「缺少的信息不应猜测补全」**保持 1.0 并如实记录**，不做猜测性调整。

**⑨ 全图没有死循环**

374 个脚本 / 380 条 `07` 边，共 **18 个环，全部是游戏正常的返回结构**
（`TITLE → MAINMENU → REPLAY_EXE → CCx_EN → TITLE`）。改接线之前先做过这项排查，
确认「顺序倒置」不是「循环」。

## 五、汉化

### 20. lng 位置对应：按池槽位填充

- lng 中**没有 id 字段**。引擎按播放顺序把**第 N 条文本**替换为 lng 的第 N 条目。
- **严格等式**：`lng 条数 == `14` 条数 + Σ(0f 的 count)`。`14` 与每个选项条目**各占一个槽位**
  （一张 `0f` 表的 `count` 个条目各占一槽，`strid` 即槽位序），不是整张表占一槽。
- 占位行（`%N`/`%P`）同样消耗条目。
- 转换产出必须按其对话流**重新生成配套 lng**（对话 id 已原样保留，可借「CCS 序号 =
  WSC id + 1」从汉化组译文逐句生成）。
- 说话人名（`0x15 %LC<Name>`）**不经 lng 替换**，走 `NameTable.txt`（见 9.）。

### 21. lng 与 ws2 池位错位：CCS 并非与 ws2 一一对应

**症状**（实机报告）：`[樱庭]'用这台ＮＥＷ自行车……'` 的名字框没显示樱庭；而旁白
`游戏里常见的奥义特效……` 却配上了「冬子」的名字。

**根因**：引擎按「`14`/`0f` 出现序」把 `lng[k]` 填进第 k 个池槽位，而现有 lng 是 Res303
按**汉化组 CCS 的行序**逐行抄的 —— **CCS 会把一句英文拆成两行中文**。一旦某处不是 1:1，
其后所有条目就整体错开，于是「名字框（来自脚本 `%LC`）× 正文（来自 lng）」对不上。

```
ws2[128]  She hit me so hard, I actually saw lights, like effects from a video game.
          ├ CCS[129] %FF%LC　桐原流奥义积极直击
          └ CCS[130] 游戏里常见的奥义特效浮现于脑海之中。
ws2[129]  \dHelp us clean up the camp.\d  (Touko)   ← lng 却取了 CCS[130]，错位一格
```

**处理**：`script/realign_lng_to_ws2.py` —— 按「**中文几行就几行**」**给 ws2 插入 `15`+`14`**
（不是把两行中文压成一条 lng），两行中文各占一个池位、lng 也各是一条。插入会变长，
故 `06`(+1) / `01 mode=0x85`(+12) 的绝对偏移要重算；`14` 的 id 与 `0f` 的 strid 是
**池槽位序**，插入后整体顺延。

**规则设计：只判高置信度的简单情形。** 方针是「规则不求判准所有文本，只判简单情况来缩小
范围，其余交给人工比较」。最终只保留一条物证：

```
merge    ← 仅 pct：CCS 有一行是 % 开头的特效/控制行（引擎指令，天然属于同一句）
separate ← 其余一律（不合并 = 保持原样，无风险）
```

**被证伪并弃用的判据**（都曾写进代码，均因发现问题而撤掉）：

| 判据 | 证伪案例 |
|---|---|
| `long`：英文 ≥60 字符即拆 | `CCA0027_en` 池位 19 的 `*insert crazy onomatopoeia equivalent to such an attack*`（61 字符）语义上就是 CCS 的一句 |
| `half`：CCS 首行不以句末标点结尾 | `\dYeah?\d`（13 字符）配 `哎呀——`／`所以说，放心吧……`，明显不该拆 |
| `both_end` / `tiny` | 仅用于**缩小待比较范围**，不参与最终判定 |

**规模**：全语料 578 处 1:2 候选 → 规则自动判掉大部分 → 剩 **34 条**进待比较列表，
逐条审完结论全是 SEPARATE。**最终只对 1 处插入新行**。这个规模是可行的 ——
规则的价值在于把 578 缩到 34，不在于判准 578。

> **「以中文为准」= 中文几行，ws2 就给几个槽位（插入 `15`+`14`），而不是把多行中文并成
> 一条 lng。** 措辞上不要用「合并」—— 它描述的是对齐关系，而实际动作是**插入**。

**幂等性的两个坑**：`realign` 会**改变自己的输入**（插入新行），因此必须让「处理过的输入」
不再触发规则，否则流水线复跑会不断累积插入：

1. **前半句的控制符要改成 `%K`** —— 拆分时把原 `14` 的 `%K%P` 换成 `%K`，
   二次运行 `ctrl_suffix(...) == '%K'` 一看便知「已拆过」，不再重复插入。
2. **插入行的兜底正文要「结构上不可能」命中判据** —— 去掉行首 `%`（否则 `pct` 命中）、
   截到**严格小于**阈值（等于也不行，边界会漏）。

**伴随修掉的两个 bug**：

1. `tool/lng.strip_speaker_wrap` 只认 `“…”`，漏掉 `‘…’` —— 这正是
   `[樱庭]'用这台…'`「角色名提取失败」的直接原因（CCS 里两种引号混用）。
2. `ws2_pool` 曾把**整张 `0f` 表**算作 1 个池位，而实际**每个选项条目各占一槽**（与 20. 同一条规则）。

### 22. 选项槽位错位：lng 少一条，其后整体提前一格

**症状**（实机报告）：一组两个选项，**第一个选项的译文显示在台词槽位、第二个选项显示成
第一个、最后一个选项槽位取不到**。

**根因**：`14` 与 `0f` 共用同一个字符串池（8.），引擎拿**池位置**去查 lng。
`CCA0004_en.lng` 只有 **152** 条，而该脚本的池需要 **153** 槽（151 句对话 + 2 个选项）——
**少一条**，于是某个位置之后整体**提前一格**：

```
池位150  英文 "What to do...%K"    lng = "去天台"       ← 选项1 的译文占了台词槽位
池位151  选项1 "Go to the roof"    lng = "和冬子说话"    ← 选项2 的译文占了选项1
池位152  选项2 "Talk to Touko"     lng = **越界**        ← lng 只到 151
```

实测该 lng **从第 0 条起就提前一格**，所以缺的那条在**头部**。补入
`早上了啊……%K%P`（= 源第 1 条的译文，控制符照抄该句 ws2 正文）后 152 → 153，
三个选项槽位全部对上。

**工具**：`script/audit_choices.py` 做三项检查 —— ① 池位连续性（`14` 的 id 与 `0f` 的 strid
必须落在同一条连续池序列上）；② `lng 条数 == 池槽位数`；③ 选项槽位内容形态（选项译文应是
短句，不应是带 `%K`/`%K%P` 的长台词）。全量扫 50 个含选项表的脚本、127 个选项条目，
**只有 `CCA0004_EN` 一处**命中。

**注意**：汉化组 CCS **不含选项译文**（`CCA0004.CCS` 只有 145 行台词；源 WSC 的 `0x02` 里
选项是日文）。选项的中文是 Res303 另行补的，所以**不能**靠重建 lng 来修选项 ——
必须保留原条目、只做整体偏移校正。

### 23. lng 语义复审：模型、边界与结论

Res303 的对齐流水线在**条数相等时按序直接 zip、不做任何相似度检查**，而其自述报告
`TEXT_QA_PASS: false`。而「条数相等」不代表「内容对应」—— Steam 删节时会**插入 `%N`/`%P`
控制行**，旧 lng 的槽位就对不上了，表现为**某处之后整体后移**。

**复审模型**：lng 第 N 条 ↔ 脚本第 N 个 `14`（见 20.）——控制行 → 该条也应是同名控制符；
其余 → 应是源 CCS 第 n 条的译文（n = 到这句为止的非控制序）。

**关键边界：只在「非控制行数 == 源 CCS 行数」时才用这个 1:1 模型。** 依据是「ws2 的对话序列
是源序列的**子序列**（MoeNovel 只删不重排）」—— 等数量 + 子序列 ⇒ 逐条恒等，此时模型**可证**。
不等时模型不成立：12 个宿主里 `CCC0000_en` 是 **211 句对源 195 行**，硬套会把前缀的译文
整体错位（实测踩过这个坑，已回退）。

**结果**：101 个脚本的 lng 与源逐条对不上，已按模型重对齐（尾部控制符照抄同一条 ws2 正文的
`%K`/`%K%P`，源覆盖不到的条目保留原值）。**跳过 50 个有 `0f` 选项表的脚本** ——
lng 槽位是字符串池位置、选项文本也占槽位，需单独处理（22.）。

**Res303 自己确认的 6 条错配**（`confirmed_live_examples`）**已全部修复** ——
它们所属的 5 个脚本正是就地插入时重建过 lng 的宿主。

**教训**：

1. **「重建后再跟模型比」是循环论证**，永远归零。校验必须来自**模型之外**的约束
   （这里是「等数量 + 子序列 ⇒ 恒等」）。
2. **说话人一致性是个好信号但会被下标漂移污染**：Steam 删节后整体错位，说话人会成对交替
   （`Taichi≠见里; Misato≠太一`），那不是 lng 错。用它做 triage 可以，做判据不行。
3. **汉化组 CCS 用简体说话人名，`SPEAKER_MAP` 的键是日文名**（`见里` vs `見里`），
   直接比会大面积假阳性 —— 需从共现统计推导映射，不要硬编码。

## 六、工程事故

### 24. 安装包哈希校验失败：元数据成员顺序与产物不一致

**症状**：制作安装包时，安装器自检报 `Voice.arc: 哈希不匹配`。

**排查**（先逐成员比内容，再比顺序）：

1. 算三方 SHA256：`asset/Voice.arc` **与 `METADATA.json` 的 checksum 一致**，
   手动覆盖到 Steam 目录的那份也一致。**所以「修改没应用上」不成立** —— 产物本身是对的。
2. 逐成员核对「`backup/` + `payload/Voice_patch.arc` → `asset/`」：30288 个 keep 成员、
   2128 个 added 成员内容全对、无缺失无多余。内容层面完全正确。
3. 比**顺序**：`METADATA.members` 与 `asset/Voice.arc` 的成员顺序**不一致**。

**根因**：`script/generate_payload.py` 的 `build_archive_delta` 按「原档顺序 + 把 asset 独有的
成员追加在末尾」生成成员表，而安装器的 `merge_arc` 是**按这张表重排**成员的。两者对不上，
重放出来的归档**成员内容都对、但字节序不同** → SHA256 必然不符。

**为什么只有 Voice.arc 中招**：`backup/Voice.arc` 本身就是按名字排序的，而
`import_missing_voices.py` 把新语音**插到各自的排序位置**以保持有序 —— 于是 asset 的实际
顺序 ≠「原档 + 追加」。其余 4 个归档的成员顺序恰好就是「原档 + 追加」，所以一直没暴露。

**为什么没早发现**：`generate_payload.py` 里本就有回读校验 `verify()`（用 backup + payload +
metadata 重放安装流程，核对结果与 asset 字节一致），**它被整段注释掉了**。它是唯一能抓住
此类问题的检查。

**修复**：① `build_archive_delta` 改为**完全按 asset 自己的成员顺序**生成；仅原档有的成员
作为 `deleted` 追加在末尾（安装器会跳过，位置无关）。② 恢复 `verify()` 并接回 `main()`；
顺带修掉它在项目内 `import tool.install` 失败的问题（把 `tool/` 放进 `sys.path`）。

**教训**：

- **「哈希不符」先分「内容 / 顺序」两层查**。逐成员比内容能立刻排除「修改没应用」，
  把问题锁到顺序或元数据层 —— 比从头怀疑产物正确性快得多。
- **元数据描述的是产物，顺序就该取产物的顺序**。任何「按来源文件排序 + 追加」的规则，
  只要产物侧做过排序插入就会失配。
- **回读校验不能注释**。这个 bug 的内容层完全正确，只有真正重放才能发现字节序差异；
  静态比对成员集合永远抓不到它。

### 25. `.git/lfs/tmp` 堆积写满磁盘

**症状**：写文档时报 `ENOSPC: no space left on device`，磁盘 100% 占用。

**根因**：`.gitattributes` 里 `*.arc filter=lfs` —— **所有 `.arc` 都走 Git LFS**，而 `asset/`
里有几百 MB 的归档。每次 `git status` 都会触发 `git-lfs filter-process` 对大文件做 clean，
把内容写进 `.git/lfs/tmp`。真正致命的是**进程泄漏**：现场有 12 个 `git-lfs.exe` 进程
（各仅 ~2 MB 内存，持续堆积 1.5 小时），`.git/lfs/tmp` 累积到 **153 GB**
（而 `.git/lfs/objects` 只有 5.7 GB）。

**处置**：

```bash
taskkill //F //IM git-lfs.exe     # 必须先杀进程，否则会边删边写
rm -f .git/lfs/tmp/*              # tmp 是临时目录，不参与对象完整性
```

**教训**：

- **`.git/lfs/tmp` 是临时目录，可安全清理**（真正的对象在 `.git/lfs/objects`）；
- **`git-lfs.exe` 进程数异常即是告警** —— 正常情况下不该有十几个常驻；
- 数百 MB 的二进制放进 LFS，在 `git status` 频繁的仓库里是实打实的负担；
- **根治仍未执行**：把 `asset/*.arc` 移出 LFS 跟踪（`.gitattributes` 排除 + `git rm --cached`），
  涉及已提交的 LFS 指针，需专门规划迁移。**这条已多次造成事故，应尽快处理。**
