## 方法论（判据与验证）

### 字节覆盖不构成正确性证明

反汇编器只要能在**错误的位置重新同步**，覆盖率检查照样通过；**自带发射器 + 自带解析器互相验证是循环论证**。
能打破循环的只有第二实现或原生语料统计（本项目的判据是原生语料的**位置直方图**）。

**错误会被对称复制**：文档里写错的字节模板会被下游实现原样继承（上游补丁侧的转换器正是照抄本文档早期写法，
而它自己的 27 项回归测试全部通过 —— 因为它的发射器与解析器同样对称）。

### 判据的可靠性先于数字大小

一个 94% 但配对无保证的统计，比一个 33% 且配对唯一的统计**更不可信**。
实例：两引擎的「事件数」不同（Steam 每更新一次 `46` 就多一个快照，帧数比约 2.3:1），
「按出现次序 zip」给出的 846 例、94% 强对应，换成「源侧帧唯一 → 配对强制」后同一批数据只剩 33%。
⇒ **配对方法是结论的一部分**；改用不依赖对齐的判据（族指纹、帧内集合、留出法）后结论才稳定。

### 先找同引擎的官方样本

「实测优先」之前先问：**这个机制在同引擎的别的游戏里长什么样**。名字替换表的规则就是从 A Sky Full of Stars 的
**官方简中包**对照出来的（前提是有一份**未加密的同引擎 exe**：CC 自己的 `.text` 段加密，ASF 仅差 0.01 版本且明文，
结论可直接外推）。但**有明文样本也别放弃静态分析**：本项目的「脚本内窄字节 = CP932」与「表键必须等于脚本标记」
两条关键结论都来自逆向。

### 偏移假设必须用全区间扫描排除

「我记得应该从这句开始」在拼接脚本时不可靠；**局部匹配不是证据**（前几条看起来对也可能是巧合）。
做法：**对每个候选偏移做全量比对**，只有真实偏移能让全部条目零误差。

### 不能盲信第三方产物，也不能盲信外部复审

- **第三方声称「适用」不等于能跑**：上游补丁未经 Steam 版测试，把它的 `Rio.arc` 直接覆盖到游戏目录会崩溃
  （其还原脚本的指令格式与 Steam 引擎多处不兼容）。必须实测。
- **外部复审的正确用法是「提出假设」**，验证仍要回语料 —— 逐条采纳/驳回，没有整体接受或整体否定。
- **不要过早收窄假设范围**：连续两次同类修复失败后就应转向更基础的假设。
- **报告结论必须独立复算**（本地重建 + 逐字节比对），不直接采信第三方报告的状态码。

### 「我没看到」不等于「不存在」

最贵的一次错误：查了 `34`/`37`/`39`/`64` 之后断言「Steam 侧没有坐标字段 ⇒ 位置由槽号承载」，
并用三条「验证」把它包装成结论 —— 那三条其实**只证明了「槽不是角色位」**。
真相是位置一直在 **`46 MoveBackground`** 里，只是当时没去看那条指令（名字像给背景用的）。
⇒ 说「两侧表达方式不同」之前，先把指令表过一遍；**推论要标成推论**，并检查结论与证据的跨度。

### 闸的通用要求

① **通过消息必须带它实际核了多少**，**计数为 0 即视为失败**（`if n == 0: fail(...)`）；
② **失败路径不得崩**：打印非 ASCII 的脚本显式设 UTF-8，且**别在消息里用 GBK 编不出的符号**（`− ≤ ≥ ⇒ ≠ ×` 用 ASCII 写）；
③ **闸写完必须接线**（流水线 + 回归清单），否则覆盖等于 0；
④ 涉及「谁在谁之后」的判据，**模型必须照抄写盘器的发射顺序**（不能顺手用数据的存储顺序 —— 既会报假错，也会放过真错）；
⑤ **跨数据源查表要显式规范化大小写/扩展名**。

## 仍未解决 / 待验证

### 立绘站位没有标定

原版 x 全是 `6.25 = 800/128` 的整数倍（原版屏幕 1/128 的栅格，34 个取值），Steam 只有 6 档站位
`{0, ±275, ±400}`（+`±399/400` 三人位外侧），必然多对一；**哪个簇对应哪一档，四种配对法互相矛盾**
（最可信的「源侧帧唯一 → 配对强制」组只有 3 个主簇、且都没有主导档位）。
`tool/wsc2ws2.py` 的 `steam_x()` 只是**单调启发式**，不是标定结果。
**精确标定需要按对白锚点对齐两侧帧**（两引擎的 `14` 对话 id 逐项相等，是天然锚）—— **尚未做**。

**已证伪、不要再走的方向**（都试过，都有数字）：

| 候选判据 | 实测 | 结论 |
|---|---|---|
| 跨引擎「原版 x → Steam 句柄」绝对阈值 | 两例自相矛盾（左者一次 st03 一次 st05） | ✗ |
| 帧级相对次序（x 升序 ↔ 槽号升序） | 同序 55% / 逆序 40% | ✗ 槽号不承载位置 |
| 按原版 `index`（位号）映射 | 65% | ✗ |
| 「首出场角色 → st03」 | 完整形式 47%（只取首出场样本虚高到 94%） | ✗ |
| Steam 槽 = 角色位 | 41 个槽装了多个角色（最多 9 个族） | ✗ 槽是**句柄** |
| 按立绘名做 LCS 对齐再统计 | 同名立绘在一个脚本里重复几十次，配错实例 | ✗ |
| 按朝向分侧 | 只能解释一部分 | ✗ 很多立绘没有朝向，作者可随时安排"违反朝向"的站位 |
| 「原版 x 单独决定站位」 | 同一 x 在不同脚本落到相反侧（各 30+ 帧且内部稳定） | ✗ 不是 x 的纯函数 |
| 「按出现次序 zip 对齐两侧帧」 | Steam 侧快照数比源侧高约 2.3 倍，中途起全是错位配对 | ✗ 统计量本身是噪声 |

**两条硬限制**：① **朝向不能当判据**；② 约 1/4 组合「两侧都用」（搭档也参与决定）。
**句柄选择的作用只有一个：别撞上宿主正在用的那一个**（同句柄 → 新图顶掉旧图；不同句柄 → 两层并存），**不决定位置**。

**「换槽前清槽」必须跨块**：给某格注入的立绘可能一直挂到**后面某个骨架 `34` 才改绑同族**（此时才撞车），
所以重建时不只处理**注入块内部**的 `34`，**骨架自己的 `34` 也要判**：同族还挂在另一个槽上就先补 `37`。
⚠️ **只清「注入来源」的槽** —— 骨架**原生就有**同族占两槽的场面（`backup` 全库 6 处），不加来源标记会改掉原生演出。

### 概率性崩溃：崩点 `AdvHD.exe+0xB61E0`（`std::list` 遍历 esi 野）—— **未根治**

見里 H 段结尾后、以及 2026-09-27 的 CCA0030「…[见里]啊?」后，都报过**概率性闪退**
（`0xc0000374` 堆损坏 / `0xc0000005`，模块 `AdvHD.exe`、偏移 **`0xB61E0`**）。
**崩点代码**（x32dbg 读 CC 运行态确认，`0x4B61E0` = `cmp dword ptr ds:[esi+8], ecx`）是一段 `std::list` 遍历：
哨兵 `eax=[ebx]`、`esi=[eax]`、`esi=[esi]` 走 next、比 `node->[8]==key`。`esi` 变野 ⇒ **链表节点被越界写坏**；
`0xc0000374` 的**延迟检测**与此自洽（真凶在更早）。
崩点属于函数 **`sub_4B5A50`**（`__thiscall`，`ecx`＝this；栈 `0x94`、带 SEH；长约 `0x790`）——
该函数按 **`std::wstring` key** 查上面那条链表，**未命中就 `operator new(0x2C)` 造一个含 wstring 的节点插进去**
（`0x4B5B60`–`0x4B5C54`），是「**文件名 → 数据**」的缓存表（与首例记录的"按文件名"一致）。
它**无符号、也无直接 xref**（像是经 vtable 调用），静态再往下推困难。

首例（見里 H 段）归因「崩点场景语音全是导入的 44100」⇒ 处置「导入语音统一重采样 48000」，复测不再复现。
**2026-09-27 复发 ⇒ 未根治**。复发时实测排除（各有证据）：asset 语音 **16696/16696 全 48000**；
Vorbis 头（版本/声道/blocksize `0xB8`/framing）与末页 EOS 与原生**逐项一致**、时长极值正常；
`.soundlevel` 缺失**在代码层无害**（`sub_500D90` 打开 `<名>.soundlevel` 失败即跳过）；
崩点场景（`CCA0030_EN`）该区与 Steam 原生**逐指令一致**；Chip2 的 `1280×960` 是原生就有的尺寸族；movie 音轨也是 48000。

**开放项**：真凶 = 谁越界写坏了这个 list 节点。

**最新线索（2026-09-27，待验证）**：崩点函数 `sub_4B5A50` 用**全局存档目录**
（`%USERPROFILE%\Saved Games\MoeNovel\<英文标题>\`）拼 **`MessageFlag.dat`** 再查表 ⇒
它与那个"已读消息"文件有关。`MessageFlag.dat` 的每条记录 = `脚本名(UTF-16LE,NUL)` +
`u32 a` + **`u32 b`** + `u32 0` + **位图**（每消息 1 bit，长度 `b/8`），而 **`b` 恰等于该脚本在产物里的 `n_final`**
（实测 `CCA0001_EN` b=32=n_final、`CCA0003_EN` b=210=n_final、**`CCA0002_EN` b=233=n_final 而 n_steam 只有 232**）。
⇒ **假设**：`MessageFlag.dat` 写的是"脚本的消息数 + 已读位图"；**补丁改变了消息数（插入/删格）**，
若该文件的记录还是**旧补丁**写的（`b` = 旧值），引擎按旧长度处理、按新消息数访问 ⇒ **越界** ⇒ 堆破坏 ⇒ 崩。
这能解释"概率性"（越界是否致命）与"某台能复现某台不能"（**取决于该文件的当前内容**）。
**验证**：把 `CCA0002_EN` 记录的 `b` 从 `233` 改回 `232`（或删掉整个 `MessageFlag.dat` 让它重建），跑同一处看是否复现。

**手段**：在 `0x4b61e0` 挂**条件断点**（`bp 0x4b61e0,esi<0x10000`，命中即停），
或让**能复现的机器**配 WER LocalDumps 抓 full dump（`0xC0000005` 是未处理异常，WER 能抓到）。
⚠️ 44100 那条是**强相关而非已证**（无对照、无次数/N），**已复发**；重采样本身可原样回滚。

### 派生缓存：能直读源就别落副本

**规则**：凡是能从仓库里已有的东西现算出来的（归档成员、索引），**不落副本**，由消费方**直读源**。
本项目的落点：`apply_text_map` 的每格英文由 `en_of_from` **从输入归档的指令流直读** ⇒
不存在「缓存过期 ⇒ 静默走样」这条路径 —— 这条规则是被真实事故换来的（缓存路径失效后读空 ⇒
尾标记整体丢失，而当时所有闸照过）。同一条口径也用在了语料上：原生 WS2 **直读 `backup/Rio.arc`**，
不另存一份副本。

### Steam 自带录音与正文错位

`CCA0019_EN` / `CCB1009_EN`（姊妹对）里「大叔们」那格播的是**上一段「古生代」那句**的声音。
**定案不靠听**：原版 WSC 逐行 + **20ms RMS 包络互相关**（Steam 英文按日配时间轴录制，同行英日两版逐帧同长 ⇒ 同行相关 `+1.000`、异行 `≈0`）。
该格挂的 `TOM_0077` 与 r80 那句的原配 `YKI028A0019` 相关 `+1.000`、与 r87 自己的 `YKI030A0019` `+0.027`
⇒ **Steam 把 r80 的英文录进了 r87 的槽位**，而 r87 自己的英文**全库不存在**。
**处置**：换挂原版日配 `YKI030A0019.OGG`（`voice_plan.json` 登记补挂、`text_map_vc.json` 的 `del2e` 删借用录音）。
**这是 Steam 自带的错配，非补丁引入**。
⚠️ **遗留**：`voice_plan.json` 被 `build_voice_plan.py` **整体重写**，而该生成器不认「已挂但内容不符」⇒
这类手工条目（本例与 `CCB2019` 的 `k123`/`k137`）**重跑生成器会丢，需重加**。

### `asset/*.arc` 移出 Git LFS（根治未执行）

`.gitattributes` 里 `*.arc filter=lfs` 让每次 `git status` 都触发 LFS 对大文件做 clean，写进 `.git/lfs/tmp`；
进程泄漏时（现场 12 个 `git-lfs.exe`）该目录曾累积到 **153 GB**（而 `.git/lfs/objects` 只有 5.7 GB）。
**临时处置**：`taskkill //F //IM git-lfs.exe` 后清 `.git/lfs/tmp/`（它是临时目录，不参与对象完整性）。
**根治**：把 `asset/*.arc` 移出 LFS 跟踪（`.gitattributes` 排除 + `git rm --cached`）—— **已多次造成事故，应尽快处理**。

## 结论（可直接引用）

### 原版与 Steam 是两套引擎：二进制不通用，内容可对位

| 特性 | 原版 `CROSSCHANNEL.exe` | Steam 版 `AdvHD.exe` |
|---|---|---|
| 脚本格式 | `WSC`（纯二进制） | `WS2`（rot6 混淆） |
| 立绘格式 | 未见 PNA，走 `ANM`/`MSK` 分类 tag | PNA 图层 |
| Arc 表项 | 固定 21 字节/条 | UTF-16LE 变长名字 |
| 版权 | WillPlus / CROSSCHANNEL | MoeNovel（Amaneko 系） |

⇒ **不能把原版的归档解包后直接塞进 Steam 版**（「从原版补入资源」在二进制层面不可行），
**但内容层面完全可用**：WSC 解密（每字节循环右移 2 位）后可读出完整原版剧本，
其**文本 / 资源引用 / 插入位置**与 Steam 版一一对应，可作权威信源；**语音 OGG 是唯一可直接复用的资源**。

### Chip2 事件 CG 的前缀白名单

Steam 引擎对 `Chip2.arc` 的事件 CG 实施**前缀白名单**，只认 `EVCC` 开头；其他前缀（如 `CN_`）被**静默忽略**
（不报错、不加载 ⇒ 表现为背景一直黑屏）。**还原 CG 一律命名 `EVCC9XXX[变体].PNG` 放进 `Chip2.arc`。**

### 同名图片 ≠ 内容审查

Steam 与原版同名图片（`EVCC*`）逐对比较：**至今没有任何一例被确认是内容审查**。
⚠️ **「相似度 > 60% 即为审查」的判据是反的**：高相似恰恰说明是同一张图；局部涂改在全局相似度上几乎看不出来。
**可行判据三条并用**：① 同名；② **保宽高比 + 最优对齐后的分块局部差异**；③ 脚本层证据（原版该场景引用了它、且 Steam 同名文件画面不同）。
（那 34 对差异 >10% 的**全部是系统图**，且全部是「同名不同物」—— 原版是小尺寸 UI 元件、Steam 是整屏。）

### 姊妹场景各自都要还原

原版把**同一段剧情**在 A 章和 B 章各存一份脚本（编号规律 `CCA00nn` ↔ `CCB10(nn-9)`，全语料 **26 对**，
台本 99% 相同、语音同套文件）。**两者都可正常到达 ⇒ 各自都要还原、不能合并。** 相关副作用：
`Rio.arc` 里内容相同的 `.lng` 由此解释（不是冗余）。

### 内容还原的三种差分形态

| 形态 | 形状 | 处置 | 判据 |
|---|---|---|---|
| **改写** | 行数一一对应、位置没错、内容换成别的段子 | 该格取原版那一行（位置对位） | 行号连续、格数 = 行数 |
| **整段删 + 新写** | 原版一段被删；Steam 在**同位置**写了新内容 | 新写保留；被删的走还原插入 | 段级行数对不上；原版录音全表无锚点 |
| **压缩概述** | 原版一段被删；Steam 用**几格概述**压掉（格数 < 行数） | 那几格改取原版首 N 行 + 其余行插入其后 | 那几格正落在缺口位置、连读恰是整段概述 |

- **不能用「语义对不上」判「Steam 新增」** —— 被改写/被压缩的格语义本来就对不上；要问「这几格是不是在替掉缺口里的那几行」。
- **机械形状可圈位置，但不能定案**：候选要逐处语义判断。
- **「别处读得到」是重要反例**（`CCB0013`、`CCD3003A/B` 都是回述）—— **成段还原会让玩家读两遍**；区分靠**恒定偏移 + 同文条数 + 语音锚点**三证。
- **删原版时语音通常一并删**（原版录音在 Steam `Voice.arc` 里全表无锚点 = 「整段删」的硬证据）。
- ⚠️ **扫描有盲区**：缺口里**没有文字格**的（纯空缺口）不会被差分扫描报出。

### 删格判据只认「整行」，子串＝半行

判「这格能不能删」看它**承载**的是哪条原版行；但「不承载任何行」**不等于**可删 ——
若它的正文恰是某条**仍被承载**的原版行的**真子串**（被切开的半行），删了句子会从半句开始/半句收尾。
判据：`equal` 整句才算重复、可删；只是子串 ⇒ 半段 ⇒ **禁删**。

### 名字框是「继承」语义

`15` 只对它**后面第一条** `14` 生效；某格**不自带 `15`** 时沿用上一格的人名。
⇒ **插入段发完必须恢复现场**（重发进入时那条名字框），否则紧随的原始格会张冠李戴；
改写名字的代码若只在「该格自带 `15`」时才动手，会**静默跳过** —— 该格没有就**主动补一条**。

### 位置表文本的复核：两把机械标尺

1. **锚点逐字符对账**：对齐正确时 `lng[k] 去标记后 == 其锚点 CCS 行的中文`，**可判定、不需语义判断**。
   搜索偏移必须 **d=0 优先**、再按 |d| 递增（否则 `……` 这类重复串会先命中假偏移）。
2. **保序覆盖对账**：把 lng 每行回查源 CCS 中文列，贪心保序分配行号，量化
   **未使用的 CCS 行（内容丢失）／重复使用（玩家可见重复）／次序回跳（乱序）**。

⚠️ **向 Steam 英文对齐是错误方向**（英文是 MoeNovel 的改写，不是权威信源）；目标序列只能是 **CCS 中文列**。
⚠️ **分支字母脚本必须先剔除**（`CCD1001A_EN` 的源覆盖 A/B/C/D 四个分支，逐行对账会产出几千条假「丢失」）。
⚠️ **无源（机翻）脚本是最大盲区**：「是否忠实英文」对机翻几乎恒真，须换判据（**术语/人名一致性可机械核验**）。

### 安装包元数据必须取产物的成员顺序

`generate_payload.py` 的成员表若按「原档顺序 + 追加」生成，而安装器**按这张表重排**，
重放出来的归档会**内容全对、字节序不同** ⇒ 哈希必然不符。
⇒ 元数据描述的是**产物**，顺序就取**产物自己的**顺序；**回读校验（重放安装流程）不能注释掉**（它是唯一能抓到此类问题的检查）。

### 写盘器只允许原样透传

重发指令流的代码**不得做「精简/去重」**：曾经用「缓冲 + 覆盖」压掉原生的 `15` 成对结构
（`14 15[] 15[名] 14` → `14 15[名] 14`），全库 273 个脚本因此偏离原生写法，且让「按单格删」无法安全实现。
任何精简都要**先拿 `backup` 实测证明原生如此**。原生口径：每句都是 `15[设名] 14 15[清框]`，
旁白也发空前缀、同角色连排也重发；**`%N`/`%P` 纯标记格不带 `15`**；背景块/出口/选项表前都不清框。
